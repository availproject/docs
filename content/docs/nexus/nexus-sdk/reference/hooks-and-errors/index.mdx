The Nexus SDK lets you gate and observe each operation through per-operation hooks, and reports every failure as a typed `NexusError`. This page gives an overview of the hooks, then covers error handling in detail.

## Hooks

There are no global hook setters. Hooks are passed **per operation** in the second `options` argument.

| Method | Review hook | Other callbacks |
| --- | --- | --- |
| `swapWithExactIn()` / `swapWithExactOut()` | `options.hooks.onIntent` receives `IntentHookData` (`quote`, `execution`) | `options.onEvent` |
| `swapAndExecute()` | `options.hooks.onIntent` receives `SwapAndExecuteHookData` (`intent`) | `options.onEvent`, `options.beforeExecute` |
| `execute()` | — | `options.onEvent` |

### Swap review hook

`hooks.onIntent` receives the server quote before anything is signed. The operation waits until you call `allow()` or `deny()`. Returning from the callback does not accept the quote.

```typescript title="TypeScript"
import type { IntentHookData, SwapOperationOptions } from '@avail-project/nexus-core';

declare function showReview(hook: IntentHookData): void;

const options: SwapOperationOptions = {
  hooks: {
    onIntent: (hook) => {
      // hook.quote: input, output, fees, allowances, plan, sourceVerdicts, expiresAt
      // hook.execution: { possible: true } | { possible: false; cause: 'not-connected' | 'insufficient-balance' }
      showReview(hook); // call hook.allow() or hook.deny() when the user decides
    },
  },
};
```

`await hook.refresh(sources?)` returns a complete replacement `IntentQuote`. Render the returned quote and read `hook.execution` again before allowing. If you don't pass a hook, the quote is accepted automatically.

See [Review Quotes](/docs/nexus/nexus-sdk/reference/swap-methods/review-quotes) for the full `IntentHookData` and `IntentQuote` shapes, slippage and timeout options, and disconnected rate previews.

### Composite review hook

`swapAndExecute()` also takes its review hook under `options.hooks.onIntent`. The hook receives `intent` (a `SwapAndExecuteIntent`), not `quote`. The intent describes the execution requirement, available balances, the shortfall, and `executionMode` (`'wallet'` or `'provider'`). `intent.quote` exists only when `intent.swapRequired` is `true`. The hook runs even when no swap is required.

```typescript title="TypeScript"
await client.swapAndExecute(params, {
  hooks: {
    onIntent: ({ intent, allow }) => {
      console.log(intent.executionMode, intent.executeRequirement, intent.shortfall);
      if (intent.swapRequired) console.log(intent.quote.output);
      allow(); // In an app, call after the user confirms.
    },
  },
});
```

### beforeExecute

`options.beforeExecute` on `swapAndExecute()` receives a `BeforeExecuteContext` (`receivedAmountRaw`, `executeAmountRaw`) and can return `{ data?, value?, gas? }` to override the destination call. In wallet mode it runs after funding. With provider destination execution it runs **before review**, and again on every refresh, so it must be safe to repeat.

See [Swap and Execute](/docs/nexus/nexus-sdk/reference/swap-methods/swap-and-execute) for the composite intent shape, `refresh`, and `beforeExecute` semantics in both execution modes.

### onEvent

Every operation accepts `options.onEvent`. Swap operations and `swapAndExecute()` emit `IntentEvent` (`quote`, `step`, and `status` events). See [Swap Events](/docs/nexus/nexus-sdk/reference/swap-methods/swap-events).

### Callbacks and flow control

- **`onEvent` never breaks a flow.** The SDK calls it without blocking. If your handler throws, the SDK logs a warning and the operation continues.
- **`onIntent` controls the flow.** Calling `deny()` rejects the operation with a `UserActionError` (`ERROR_CODES.USER_INTENT_HOOK_DENIED`). If the hook throws or returns a rejected promise, the operation rejects with that error.
- **Await `refresh()` before calling `allow()`.** A failed refresh rejects the `refresh()` promise and keeps the previous quote or intent.
- **Event handlers only show progress.** Always `catch` the operation's promise to handle the final failure.

## Error handling

Every SDK operation rejects with a typed `NexusError` subclass. Operations never resolve with an error result.

### The NexusError hierarchy

`NexusError` is the abstract base class. Each exported subclass pins a `category`:

```typescript title="TypeScript"
abstract class NexusError<C extends ErrorCategory = ErrorCategory> extends Error {
  readonly category: C;                     // set by each subclass
  readonly code: ErrorCode;                 // e.g. 'backend/insufficient_balance'
  readonly context: ErrorContext<C>;        // { operation?, service?, stepId?, stepType?, chainId? }
  readonly details?: Record<string, unknown>;

  toJSON(): object; // { name, message, category, code, context, details }
}

type ErrorCategory =
  | 'validation'
  | 'user_action'
  | 'simulation'
  | 'execution'
  | 'backend'
  | 'external_service'
  | 'internal';
```

| Subclass | `category` | `context.service` | Meaning |
| --- | --- | --- | --- |
| `ValidationError` | `validation` | — | Caller input or precondition failure: invalid params, unsupported token or network, insufficient local balance, SDK not initialized, wallet not connected. |
| `UserActionError` | `user_action` | `'wallet'` or `'hook'` | The user declined: review hook `deny()`, a signature, an approval, or a transaction prompt. |
| `SimulationError` | `simulation` | `'rpc'` | A pre-execution simulation failed. Simulation failures reported by the middleware use `BackendError` with `backend/simulation_failed`. |
| `ExecutionError` | `execution` | `'wallet'` or `'rpc'` | Runtime failure at the wallet or RPC boundary: send, confirm, revert, gas or fee estimation, balance read. |
| `BackendError` | `backend` | `'middleware'` | An Avail middleware failure, including quote, routing, provider, submission, and fulfillment errors. |
| `ExternalServiceError` | `external_service` | for example `'coinbase'` | A third-party dependency failed, such as the Coinbase exchange-rate lookup. |
| `InternalError` | `internal` | — | An SDK invariant was violated. Report these. |

- `category` answers "whose fault is it". Branch on it, or use `instanceof`, for coarse handling.
- `code` answers "what happened". It's a stable string shaped `category/specific_name`. Compare it against `ERROR_CODES.*` for specific recovery.
- `message` is user-presentable. The underlying wallet, RPC, or HTTP text is inlined into it.
- `context` carries `operation`, `service`, and, for step-scoped failures, `stepId`, `stepType`, and `chainId`.
- `details` carries operation-specific metadata. Middleware failures include `error` (the original server message), `middlewareCode`, `middlewareSubcode`, `errorId`, `middlewareDetails`, and `httpStatus`.

<Callout type="info">
Errors are flat. There is no `cause` chain and no `NexusStepError`: step-scoped failures are the applicable subclass with `context.stepId`, `context.stepType`, and `context.chainId`. The SDK deliberately doesn't ship a `userMessage`, `isRetryable`, or `formatError()` helper, so map `code` to your own UX. Keep `code` and `details.errorId` for support requests: the middleware logs the same `errorId`.
</Callout>

### Recommended pattern

```typescript title="TypeScript"
import {
  ERROR_CODES,
  NexusError,
  UserActionError,
  getIntentQuoteFailure,
} from '@avail-project/nexus-core';

try {
  const result = await client.swapWithExactOut(
    { toChainId: 8453, toTokenAddress: baseUsdc, toAmountRaw: amountRaw },
    swapOptions,
  );
  console.log('Fulfilled', result.intentExplorerUrl);
} catch (error) {
  if (error instanceof UserActionError) {
    // The user declined a prompt or denied the review. Usually no error toast.
    console.info('Action declined', error.code);
  } else if (error instanceof NexusError) {
    switch (error.code) {
      case ERROR_CODES.WALLET_NOT_CONNECTED:
        showMessage('Connect a wallet, then request a fresh quote.');
        break;
      case ERROR_CODES.BACKEND_INSUFFICIENT_BALANCE:
        showMessage('Fund the wallet or choose different source assets.');
        break;
      case ERROR_CODES.BACKEND_INSUFFICIENT_APPROVAL_GAS:
        showMessage('Add native gas on the source chain or choose another source.');
        break;
      case ERROR_CODES.BACKEND_VALUE_ABOVE_CEILING: {
        const maxValueUsd = getIntentQuoteFailure(error)?.details.maxValueUsd;
        showMessage(`Reduce the amount (limit: $${String(maxValueUsd)}).`);
        break;
      }
      default:
        showMessage(error.message);
    }

    const failure = getIntentQuoteFailure(error);
    if (failure) console.log('Quote diagnostics', failure.subcode, failure.sourceVerdicts);
    if (error.details?.approvals) console.log('Broadcast approvals', error.details.approvals);

    reportToSupport(error.toJSON());
  } else {
    throw error; // Not from the SDK
  }
}
```

### Error codes reference

`ERROR_CODES` is an exported constant that maps friendly keys to `code` strings, for example `ERROR_CODES.BACKEND_INSUFFICIENT_BALANCE === 'backend/insufficient_balance'`. Compare against the constant rather than the literal string, and never parse `message` text.

The codes below are the ones integrators most often handle. The exhaustive map is in [`src/domain/errors.ts`](https://github.com/availproject/nexus-sdk/blob/main/src/domain/errors.ts).

#### Validation and user action

| `ERROR_CODES` key | `code` | When |
| --- | --- | --- |
| `INVALID_INPUT` | `validation/invalid_input` | Invalid params, such as a non-positive amount, a malformed address, an invalid `page`, or an unsupported provider-execution setup |
| `INSUFFICIENT_BALANCE` | `validation/insufficient_balance` | Local balance checks in `swapAndExecute()`, such as selected destination tokens no longer being available, or funds unable to cover execution value and gas |
| `TOKEN_NOT_SUPPORTED` | `validation/token_not_supported` | The token isn't supported on that chain |
| `CHAIN_NOT_FOUND` | `validation/chain_not_found` | The chain isn't supported |
| `ENVIRONMENT_NOT_SUPPORTED` | `validation/environment_not_supported` | Intent operations or async catalog helpers called on `testnet` |
| `SDK_NOT_INITIALIZED` | `validation/sdk_not_initialized` | `initialize()` hasn't completed |
| `WALLET_NOT_CONNECTED` | `validation/wallet_not_connected` | No provider is set, or `allow()` was called on a disconnected preview |
| `USER_INTENT_HOOK_DENIED` | `user_action/intent_hook_denied` | The review hook called `deny()` |
| `USER_INTENT_SIGNATURE_DENIED` | `user_action/intent_signature_denied` | The user rejected the intent signature |
| `USER_ALLOWANCE_APPROVAL_DENIED` | `user_action/allowance_approval_denied` | The user rejected an approval |
| `USER_TX_SEND_DENIED` | `user_action/tx_send_denied` | The user rejected a transaction |

#### Execution

| `ERROR_CODES` key | `code` | When |
| --- | --- | --- |
| `EXEC_TX_SEND_FAILED` | `execution/exec_tx_send_failed` | Sending a transaction failed |
| `EXEC_TX_CONFIRM_FAILED` | `execution/exec_tx_confirm_failed` | Waiting for an execute receipt failed or timed out |
| `EXEC_TX_ONCHAIN_REVERTED` | `execution/tx_onchain_reverted` | A transaction reverted on-chain |
| `EXEC_APPROVAL_TX_SEND_FAILED` | `execution/approval_tx_send_failed` | An execute approval transaction failed to send |
| `EXEC_APPROVAL_TX_CONFIRM_FAILED` | `execution/approval_tx_confirm_failed` | An execute approval transaction failed to confirm |
| `EXEC_ERC20_ALLOWANCE_READ_FAILED` | `execution/erc20_allowance_read_failed` | Reading the current allowance failed |
| `EXECUTION_ERROR` | `execution/error` | Other wallet or RPC failures, such as gas estimation or a destination balance read |

#### Backend (middleware)

Middleware failures are `BackendError`s with `context.service: 'middleware'`. A recognized middleware subcode takes precedence over the general code, and related provider failures share one SDK code (the original subcode stays in `details.middlewareSubcode`).

| `ERROR_CODES` key | `code` | Typical recovery |
| --- | --- | --- |
| `BACKEND_INSUFFICIENT_BALANCE` | `backend/insufficient_balance` | Fund the wallet or choose different sources, then refresh |
| `BACKEND_INSUFFICIENT_APPROVAL_GAS` | `backend/insufficient_approval_gas` | Add native gas on the source chain or choose another source |
| `BACKEND_NO_ROUTABLE_SOURCE` | `backend/no_routable_source` | Review `sourceVerdicts` and adjust the sources |
| `BACKEND_VALUE_ABOVE_CEILING` | `backend/value_above_ceiling` | Reduce the value; `getIntentQuoteFailure(error)?.details.maxValueUsd` is the USD limit |
| `BACKEND_INPUT_BELOW_DEPOSIT_FEE` | `backend/input_below_deposit_fee` | Increase the source amount to cover the deposit fee |
| `BACKEND_NO_ROUTE_TO_DESTINATION` | `backend/no_route_to_destination` | Choose a destination supported by the allowed providers |
| `BACKEND_TOKEN_NOT_SUPPORTED`, `BACKEND_CHAIN_NOT_SUPPORTED` | `backend/token_not_supported`, `backend/chain_not_supported` | Choose a supported token or chain |
| `BACKEND_QUOTE_UNAVAILABLE` | `backend/quote_unavailable` | Retry later or change the request |
| `BACKEND_PRICE_UNAVAILABLE`, `BACKEND_QUOTE_PRICE_OUTLIER` | `backend/price_unavailable`, `backend/quote_price_outlier` | Retry later or choose another asset |
| `BACKEND_PROVIDER_UNAVAILABLE` | `backend/provider_unavailable` | Retry; the only quote failure marked `retryable: true` |
| `BACKEND_NO_PROVIDERS_ENABLED` | `backend/no_providers_enabled` | No provider is enabled for the request |
| `BACKEND_INTENT_REFUSED` | `backend/intent_refused` | The provider refused the intent; change the request |
| `BACKEND_SAME_CHAIN_GAS_DROP_UNSUPPORTED`, `BACKEND_GAS_DROP_TOO_SMALL` | `backend/same_chain_gas_drop_unsupported`, `backend/gas_drop_too_small` | Remove or adjust `toNativeAmountRaw` |
| `BACKEND_REQUEST_EXPIRED` | `backend/request_expired` | Request a fresh quote |
| `BACKEND_RATE_LIMITED` | `backend/rate_limited` | Back off and retry |
| `BACKEND_UPSTREAM_TIMEOUT`, `BACKEND_NETWORK_ERROR` | `backend/upstream_timeout`, `backend/network_error` | Retry reads; after commitment, check status first (see below) |
| `BACKEND_RFF_SUBMIT_FAILED` | `backend/rff_submit_failed` | Intent submission failed; check status before retrying |
| `BACKEND_FULFILMENT_WAIT_TIMEOUT` | `backend/fulfilment_wait_timeout` | `fillTimeoutMinutes` elapsed; the intent may still fulfill |
| `BACKEND_ERROR` | `backend/error` | Other middleware failures, including a quote or intent that expired (`details.reasonBucket: 'expired'`) |

The middleware can also report request, signature, and permit problems (`BACKEND_INVALID_REQUEST`, `BACKEND_UNAUTHORIZED`, `BACKEND_INVALID_INTENT_SIGNATURE`, `BACKEND_INVALID_PERMIT_SIGNATURE`, `BACKEND_INSUFFICIENT_ALLOWANCE`, `BACKEND_PERMIT_RELAY_FAILED`, and others). Log these with `details.errorId` for support.

### Quote failure diagnostics

`getIntentQuoteFailure(error)` extracts structured routing, amount, balance, approval-gas, and price diagnostics from a quote failure. It returns `null` for any other error.

```typescript title="TypeScript"
getIntentQuoteFailure(error: unknown): IntentQuoteFailure | null
```

```typescript title="TypeScript"
type IntentQuoteFailure = {
  code?: string;                       // middleware code
  subcode: IntentQuoteFailureSubcode;
  errorId?: string;                    // correlation ID shared with middleware logs
  retryable: boolean;                  // true only for PROVIDER_UNAVAILABLE
  sourceVerdicts: IntentSourceVerdict[];
  providerReasons: string[];
  details: Record<string, unknown>;    // endpoint-specific, e.g. maxValueUsd
};

type IntentQuoteFailureSubcode =
  | 'NO_ROUTABLE_SOURCE'
  | 'VALUE_ABOVE_CEILING'
  | 'NO_ROUTE_TO_DESTINATION'
  | 'INPUT_BELOW_DEPOSIT_FEE'
  | 'INTENT_REFUSED'
  | 'PROVIDER_UNAVAILABLE'
  | 'NO_PROVIDERS_ENABLED'
  | 'INSUFFICIENT_BALANCE'
  | 'INSUFFICIENT_APPROVAL_GAS'
  | 'SAME_CHAIN_GAS_DROP_UNSUPPORTED'
  | 'QUOTE_PRICE_UNAVAILABLE'
  | 'QUOTE_PRICE_OUTLIER';

type IntentSourceVerdict = {
  chainId: number;
  tokenAddress: Hex;
  tokenSymbol: string;
  state: 'selected' | 'unused' | 'unroutable';
  reason?:
    | 'BELOW_DEPOSIT_FEE'
    | 'INSUFFICIENT_APPROVAL_GAS'
    | 'ABOVE_PROVIDER_CEILING'
    | 'CURRENCY_MISMATCH'
    | 'NOT_IN_PROVIDER_CATALOG'
    | 'DESTINATION_NOT_SERVED'
    | 'PROVIDER_REFUSED';
  detail?: string;
};
```

The middleware reports a specific failure (`VALUE_ABOVE_CEILING`, `INPUT_BELOW_DEPOSIT_FEE`, or `NO_ROUTE_TO_DESTINATION`) only when all unroutable sources agree on the required change. Source problems and mixed reasons stay `NO_ROUTABLE_SOURCE`, so inspect `sourceVerdicts` to tell the user which source to change. `NO_ROUTE_TO_DESTINATION` means the request's allowed providers exclude every provider that serves the destination, and the matching verdict reason is `DESTINATION_NOT_SERVED`. A destination that no provider supports still fails as token-not-supported.

Except for `PROVIDER_UNAVAILABLE`, these failures have `retryable: false`. Change the request before retrying.

### Provider destination execution rejections

With `useProviderDestinationExecution: true`, `swapAndExecute()` rejects unsupported setups before signing and never falls back to wallet execution. These rejections don't have dedicated codes:

| Condition | Error |
| --- | --- |
| The selected route doesn't support destination calls (`quote.supportsDestinationCalls` is `false`, for example because multiple funding legs were selected or the middleware is older) | `ValidationError`, `INVALID_INPUT` |
| `tokenApproval` targets a token other than the quoted output token, or the output is native | `ValidationError`, `INVALID_INPUT` |
| Native call `value` isn't funded by native output, or exceeds the execution budget | `ValidationError`, `INVALID_INPUT` |
| Exact-input output is unpriced, or too small to fit a positive reserve and execution amount | `BackendError`, `BACKEND_ERROR` |
| The final quote's minimum output is below the encoded execution budget | `BackendError`, `BACKEND_ERROR` with `details.executionAmountRaw`; refresh the quote |

### Failures after commitment

A failure before anything is signed or broadcast is safe to retry with a fresh quote. After commitment, it may not be:

- `step` events carry `committed`. Once it's `true`, a later failure doesn't mean the intent failed.
- A timeout or connection failure during submission doesn't establish whether the middleware accepted the intent.
- `BACKEND_FULFILMENT_WAIT_TIMEOUT` means `fillTimeoutMinutes` elapsed, not that the intent was lost.

In these cases, check [`listIntents()`](/docs/nexus/nexus-sdk/reference/list-intents), the intent explorer, and known transaction hashes before retrying. The intent may still fulfill. A rejected promise can follow transactions that were already submitted.

### Approval states in error details

When an ERC-20 approval fails, the SDK first settles every approval it already broadcast, then rejects. The error carries `context.stepType` (`'erc20_approval'`, or `'source_approval_signature'` for permit signatures) and `error.details.approvals`, which lists each broadcast approval:

```typescript title="TypeScript"
type ApprovalOutcome = {
  chainId: number;
  tokenAddress: Hex;
  spender: Hex;
  txHash: Hex;
  txExplorerUrl: string;
  state: 'confirmed' | 'reverted' | 'unconfirmed';
};
```

- `confirmed` — the approval is on-chain.
- `reverted` — the approval transaction reverted.
- `unconfirmed` — the receipt couldn't be confirmed. The transaction may still confirm.

Start any follow-up operation with a fresh quote, so its allowances reflect what actually landed on-chain.
